가상 스레드 식당

웨이터 비유로 시작해 mount()/unmount(), Continuation, pinning 까지. 실측 수치와 JDK 소스 근거가 붙은 개발자용 시각 덱입니다.

1

플랫폼 스레드는 왜 비싼가

웨이터(스레드)는 정직원입니다. 한 명 뽑을 때마다 OS 가 커널 스레드를 1:1 로 붙입니다. 빈 스레드 1만 개 생성이 342ms, 가상 스레드는 3ms (실측, 114배).

더 큰 문제는 블로킹입니다. DB, HTTP 를 기다리는 동안 이 비싼 스레드가 통째로 놉니다.

2

스레드 풀 - 아끼는 데는 한계가 있다

부하가 늘어도 스레드보다 큐가 먼저고, 웨이터를 5배 뽑았더니 오히려 느려졌습니다 (1ms 블로킹 태스크 2만 개 실측).

생성 비용 + 동시에 깨어나는 스레드들의 스케줄링 비용. 블로킹 처리량은 스레드 수로 살 수 없습니다.

3 · 핵심

mount / unmount - 주문서를 보드에 걸다

// VirtualThread.java:295-305 - 가상 스레드의 일생은 이 블록의 반복
mount();
try {
    cont.run();               // Continuation 실행 또는 재개
} finally {
    unmount();
    if (cont.isDone()) afterDone();
    else               afterYield();   // park 등으로 얼려진 경우
}

mount()/unmount()는 이 파일 전체에서 오직 한 곳에서만 불립니다. 블로킹된 가상 스레드는 자는 OS 스레드가 아니라 힙에 놓인 자바 객체입니다.

4

스택의 실체 - Continuation 과 StackChunk

가상 스레드가 싼 이유는 스택을 옮길 수 있는 객체로 만들었기 때문입니다. 동결 알고리즘은 자바가 아니라 hotspot C++ 에 있습니다.

doYield()는 @IntrinsicCandidate native. 실체는 continuationFreezeThaw.cpp. 자바 소스만 읽으면 여기서 막히는 게 정상입니다.

5 · 실패 모드

PINNED - 동결이 실패할 때

아직 pin: native 호출 (JNI) synchronized native 메서드 클래스 로딩·<clinit> 중 블로킹 진단: JFR jdk.VirtualThreadPinned -Djdk.tracePinnedThreads 는 제거됨

pin 되면 가상 스레드의 유일한 장점을 잃고 1번 그림으로 되돌아갑니다. 다행히 JDK 24부터 가장 흔한 원인(synchronized)이 사라졌습니다.

6 · 정산

이득이 나는 곳, 안 나는 곳

가상 스레드가 사는 것은 대기 시간을 병렬로 겹치는 능력입니다. 아무도 블로킹하지 않으면(CPU 바운드) carrier 수 = 코어 수 그대로라 이득이 0 입니다.

JEP 444: 처리량(throughput)을 위한 것이지 지연 시간(latency)을 위한 것이 아니다.

7

가져갈 것 세 줄

풀링가상 스레드는 풀링하지 않는다. 쓰고 버린다 (JEP 444 명시)
